# Задача 1 «Матчинг товаров» — рабочая область darksteeld

> Рабочая область участника `darksteeld` (GitHub: DarkSteelD). Стадия:
> **EDA и командная валидация построены (2026-08-13), реперные бейзлайны на
> лидерборде.** Исходные данные задачи читать из общей директории
> `../../data/raw/`; все производные артефакты — внутрь этой папки.

## Код

- `src/validation_baselines.py` — пять дешёвых бейзлайнов на замороженных
  фолдах (`make darksteeld-baselines` из корня).
- `src/lgbm_cheap.py` — первый обучаемый репер: LightGBM на 21 дешёвой фиче
  пары, OOF строго по замороженным фолдам.
- `src/blend_predictions.py` — взвешенное среднее OOF-предсказаний с фиксированными
  весами; бленд не модель, пересчитывать нечего.
- `src/stack_predictions.py` — обучаемый стак: логрегрессия по логитам компонент,
  мета-модель обучается leave-one-fold-out, плюс модель на всех фолдах для контейнера.
- `src/lgbm_knrm.py` — стекинг на уровне признаков: выходы двух KNRM подаются в
  LightGBM колонками рядом с 21 дешёвым признаком; режимы `insample` и `nested`.
- `src/knrm_joint_model.py` — совместная KNRM (четыре канала взаимодействия,
  общая таблица эмбеддингов, гейты по ключам поверх откликов ядер).
- `src/knrm_joint_batching.py` — обрезка паддинга и бакетирование по длине;
  без него канал атрибут-атрибут считает втрое лишнего.
- `baselines_ref/` (локально, вне Git) — распакованный
  `matching-baseline-lightweight.zip` организаторов для инспекции контракта
  контейнера.

## Отчёты по данным задачи

- `reports/DATA_EDA.md` — баланс ручной разметки, граф пар и компоненты
  (группы утечки), LLM-разметка (пересечение с ручной = 0), категории, тексты.
- `reports/VALIDATION_BASELINES.md` — фолдовые PR-AUC пяти бейзлайнов против
  публичного LB и следствия.
- `reports/STACK3.md` — стак трёх компонент (KNRM по именам, KNRM по атрибутам,
  LightGBM): корреляции, подбор весов и его измеренная цена, обучаемая
  мета-модель, замер времени контейнера и проверки архивов.
- `reports/STACK_FEATURES.md` — те же три модели, но комбинирование на уровне
  ПРИЗНАКОВ: выходы обеих KNRM внутрь LightGBM. 0.704896 против 0.683971 у стека
  предсказаний; отдельно измерена цена in-sample признака — 0.0388 PR-AUC.
- `reports/KNRM_JOINT.md` — совместная KNRM: название и атрибуты в одной сети с
  кросс-полевыми каналами. Там же разбор, почему прежнее представление атрибута
  `normalize(k ⊙ v)` вырождено (антиподы читаются как точное совпадение) и
  почему паддинг в этой архитектуре платный.

## Что здесь есть ещё

Evidence base, собранная в мета-исследовании `ozon-ecup-2026` до открытия задач
(2026-08-09), перенесена в `reports/`:

- `FAMILY_MATCHING.md` — что двигает скор в product matching, с числами:
  Shopee Price Match, Amazon KDD Cup 2022 (ESCI), WDC Products, Ditto, R-SupCon,
  MWPD2020, Rakuten SIGIR-eCom.
- `00_SUMMARY.md` — сводный отчёт кампании по всем трекам и бейзлайнам.
- `PRIOR_EDITIONS.md` — метрики, масштабы данных и контейнерные envelope
  прошлых E-CUP (2024, 2025).
- `PUBLISHED_SOLUTIONS.md` — что из решений прошлых лет публично, что клонируемо,
  какие рецепты; включая `compute_score.py` организаторов матчинга-2024
  (per-category скоринг).
- `OZON_NATIVE.md` — схема данных матчинга-2024, продакшен-стек Ozon, выбор
  русскоязычного энкодера; три нерешённых противоречия.
- `FAMILY_RECSYS_TRANSFERABLE.md` — пять переносимых находок из recsys-треков.
- `CAMPAIGN_RULES.md` — процессные правила кампании (ship gate, oracle first,
  noise floor, prereg), оплаченные предыдущей трёхнедельной кампанией.

## Первые шаги после пиновки страницы задачи

1. Считать метрику, формат данных, наличие candidate pairs, контейнерный
   envelope — до этого не фиксировать архитектуру.
2. Оракульный потолок и noise floor LB до строительства первого лейна.
3. Кандидаты энкодеров и их лицензии — по `FAMILY_MATCHING.md` §лицензии и
   `OZON_NATIVE.md` §encoder choice; лицензию перепроверять при скачивании.

# Совместная KNRM: название и атрибуты в одном пространстве

`[V 2026-08-16]` Статус: сеть реализована и покрыта тестами, предобучение на
4M пар `matches_llm` идёт. **Числа на фолдах ещё нет** — как появится, сюда же.

Две существующие сети читают по одному полю каждая, поэтому ни одна не видит
случая, когда свидетельство лежит в названии одного товара и в значении
атрибута другого: `шуруповерт bosch gsr 12v` против `бренд = bosch`. Здесь одна
сеть считает четыре взаимодействия: имя-имя, атрибуты-атрибуты и два
кросс-канала.

Код: `src/knrm_joint_model.py`, `src/knrm_joint_batching.py`,
`experiments/knrm_joint_llm/{train,finetune}.py`, тесты в `tests/` (23 штуки).

## Что заставило переделать атрибутную модель

Прежнее представление атрибута — `normalize(k ⊙ v)`, поэлементное произведение
векторов ключа и значения. Замер на **отгружаемых** таблицах (40 000 случайных
пар, 300 координат) показал, что конструкция вырождена.

**Знаки сокращаются до косинуса.** Числитель раскрывается как
`Σᵢ (k_A[i]·k_B[i]) · (v_A[i]·v_B[i])`: если по координате расходятся и ключи, и
значения, произведение двух отрицательных вкладов **положительно**. Два
несогласия дают согласие.

| | |
| --- | ---: |
| координат «оба вклада положительны» (честное согласие) | 25.3% |
| координат «оба отрицательны» (два расхождения → плюс) | 24.8% |
| **доля положительной массы числителя из координат «оба расходятся»** | **48.9%** |

Почти половина измеренного сходства изготовлена из двойного несогласия. Это не
численная неприятность, а точная инвариантность:
`slot(−k, −v) = normalize((−k)⊙(−v)) = normalize(k⊙v) = slot(k, v)`.

| подстановка | cos(slot) |
| --- | ---: |
| `k_B = −k_A`, `v_B = −v_A` — противоположны **оба** | **+1.0000** |
| `k_B = −k_A`, `v_B = +v_A` — противоположен только ключ | −1.0000 |

Противоположный ключ и противоположное значение читаются как идеальное
совпадение атрибута.

**Следствие — мёртвый банк ядер.** Докстринг прежней модели обещает, что
атрибуты, совпавшие по одной стороне, «попадают между совпадением и
несовпадением». Измерено: не попадают.

| режим | медиана cos(slot) | p10…p90 |
| --- | ---: | --- |
| ключ и значение разные | +0.0004 | −0.074 … +0.074 |
| совпал ключ | +0.0013 | −0.125 … +0.126 |
| совпало значение | +0.0143 | −0.125 … +0.156 |
| совпало всё | +1.0000 | +1.000 … +1.000 |

Частичные совпадения неотличимы от полного несовпадения. Из одиннадцати ядер на
случайных парах срабатывают **два** (mu = ±0.1, по 62%); ядра на 0.3, 0.5, 0.7,
0.9 мертвы. Банк фактически трёхмерен.

**И это, похоже, объясняет плохой перенос атрибутного канала** (public/local
0.4020 против 0.4655 у имён, см. `STACK_FEATURES.md`): модель держится почти
целиком на точном совпадении слота — совпали и ключ, и значение строка в строку.
Сигнал хрупкий: стоит тесту записать значение иначе, и подхватить нечем, мягких
ядер нет.

## Архитектура

Четыре блока сходства, все поверх **одной** таблицы эмбеддингов:

| блок | слева | справа |
| --- | --- | --- |
| N×N | токены имени A | токены имени B |
| A×A | значения атрибутов A | значения атрибутов B |
| N×A | токены имени A | значения атрибутов B |
| A×N | значения атрибутов A | токены имени B |

Три решения, которые здесь не свободны:

1. **Кросс-блоки сравнивают имя со значениями, без ключей.** Косинус между
   токеном имени и произведением `k ⊙ v` не имеет смысла — произведение
   искажает направление. А когда свидетельство мигрирует между полями, несёт его
   значение; ключ — метаданные о том, где оно лежит.
2. **Таблица общая.** Это условие работоспособности, а не экономия памяти:
   артикул, попавший в имя A и в значение атрибута B, получает один и тот же
   вектор, косинус 1.0 и ядро точного совпадения срабатывает **через границу
   полей**. С раздельными таблицами или обучаемой проекцией `W` это свойство
   умирает.
3. **Ключ управляет откликом ядра, а не косинусом.** `вес = sigmoid(MLP(признаки
   ключей)) ∈ (0,1)` умножает **неотрицательный** отклик RBF. Гейт может только
   ослабить свидетельство, знак поменять нечем — то есть дефект из предыдущего
   раздела закрыт по построению, а не подкручен.

Симметрия точная: N×N и A×A пулятся в обе стороны и усредняются, кросс-каналы
входят только как `0.5·(z_AB + z_BA)` и `|z_AB − z_BA|`. BatchNorm нигде нет
(только LayerNorm), поэтому строка батча не зависит от соседей.

Признаки: `[z_tt, z_aa, z_cross_mean, z_cross_diff]` = 4K → MLP → логит.

## Паддинг оказался платным

Маски применяются **после** einsum, поэтому стоимость задаётся формами паддинга,
а не содержимым. Реальные данные сильно разрежены:

| поле | медиана | p90 | паддинг |
| --- | ---: | ---: | ---: |
| токенов названия | 8 | 16 | 20 |
| атрибутов | 11 | 23 | 24 |
| токенов значения | **1** | 3 | 6 |

Обрезка по максимуму батча сама по себе не даёт **ничего**: при случайном
порядке в батче из 256 почти наверняка найдётся товар с 24 атрибутами. Экономия
появляется только вместе с сортировкой по длине — расчётно стоимость канала A×A
падает до 32.8%, фактически получено **1.77×** (389 пар/с против 220): у
LLM-корпуса медиана 14 атрибутов в паре, плюс фиксированные накладные.

Порядок батчей перемешивается: однородность нужна внутри батча ради скорости, а
последовательность шагов обязана быть случайной. Тест проверяет главное —
обрезка **не меняет скор** (совпадение до 1e-10 в double).

Отдельно: `SparseAdam` по таблице вместо плотного `AdamW` дал ещё **1.61×** при
идентичной траектории loss. Плотный шаг по 283M параметров стоил столько же,
сколько весь forward, хотя за батч трогается доля процента строк.

## Стоимость `[CAMPAIGN_RULES §13]`

| | |
| --- | ---: |
| обучение | 365–389 пар/с (12 ядер CPU) |
| предобучение 4M пар | ~3 ч |
| дообучение фолда (274 240 пар × 2 эпохи) | ~30 мин |
| **инференс 365 654 пар** | 13.4 мин без бакетирования, **перемерить с ним** |

Инференс — открытый вопрос по допуску в контейнер: лимит 20 минут на **весь**
прогон, а нынешний стек из трёх компонент укладывается в 158 секунд. С
бакетированием ожидается ~7.5 мин, но это оценка, а не замер.

Корпус взят 4M, а не все 11.19M, по измеренному прецеденту: у
`knrm_attrs_llm_full` предобучение на 11.19M дало лучший zero-shot (+0.0146), но
после дообучения преимущество исчезло целиком (−0.0004). Насыщение наступает
ниже 4M. Заодно корпус совпадает с `knrm_attrs_llm` — сравнение будет чистым.

## Что проверяют тесты

Восемь обязательных случаев (симметрия, паддинг, кросс-канал на `bosch`, гейт,
знаки, пустые атрибуты, градиенты, полностью замаскированный атрибут) плюс:

* регрессия на знаковое вырождение — тест конструирует антиподы, показывает, что
  **старая** конструкция читает их как косинус +1, и проверяет, что новая ядро
  точного совпадения не зажигает;
* тождественность обрезки паддинга;
* независимость строк батча;
* отсутствие градиента у `padding_idx`.

## Открытые вопросы

1. **Скор на фолдах** — считается, будет к ~05:20.
2. **Инференс с бакетированием** — перемерить на готовой модели; от этого
   зависит, проходит ли сеть в контейнер вообще.
3. **Переносимость.** Сеть смешивает каналы внутри себя обучаемыми весами, и
   долю атрибутного канала снаружи уже не подкрутить — в отличие от линейного
   стека, где вес это число. Учитывая, что атрибутный канал переносится хуже
   (0.4020 против 0.4655), а `lgbm_knrm` погорел именно на переусилении
   атрибутов, локальный выигрыш здесь тем более не следует считать публичным,
   пока не измерен.
